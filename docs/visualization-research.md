# Stack Stats visualization research

Research date: 2026-09-25. This is a product-specific evaluation, not a claim that one chart is universally best. Implementation details and rollout belong in the accompanying architecture document; audited data fields and source paths are in [the data inventory](visualization-data-inventory.md).

## Decision

Use the public data already approved for a profile to make six distinct, customizable visualizations: horizontal bars, dots, radial rings, a polar-area language bloom, a segmented donut, and a code-change waterfall. These cover an immediately readable option, compact comparison, radial identity, and an intentionally dramatic shape without inventing time series or skill scores. The first visualization release roadmap should add two temporal families after an explicit public aggregate API is designed: daily line/sparkline and calendar heatmap. Those two are **not available from today's public profile payload**.

Use small React SVG renderers for this bounded first set. Keep the existing Recharts dependency for the existing language module. Do not add Plotly, ECharts, D3, or Visx merely to draw these shapes. Later, import a focused geometry package such as `d3-contour` when a real matrix dataset justifies it; evaluate a separately loaded scientific renderer for an explicitly selected 3D module.

## Research coverage and provenance

The [From Data to Viz catalog](https://www.data-to-viz.com/) organizes charts around input data shapes. That is a useful starting point for a compatibility system; the Stack Stats mapping below additionally checks units, publication, coverage, and semantic meaning. The [Data Visualisation Catalogue](https://datavizcatalogue.com/) supplied less conventional temporal/radial candidates, including [spirals](https://datavizcatalogue.com/methods/spiral_plot.html) and [polar area diagrams](https://datavizcatalogue.com/methods/nightingale_rose_chart.html).

The official [D3 gallery](https://observablehq.com/@d3/gallery), [Plotly scientific/3D gallery](https://plotly.com/javascript/3d-charts/), and [Plotly contour gallery](https://plotly.com/javascript/contour-plots/) demonstrate ways to render matrices, networks, distributions, and higher-dimensional observations. They do not establish that Stack Stats has the required measurements. Data Viz Project was also attempted at its [catalog](https://datavizproject.com/) and individual chart pages; the browsing tool returned HTTP 403/unavailable, so no conclusions here depend on having read it.

The compatibility judgments, names such as “language bloom,” release selection, and privacy gates below are our design recommendations based on the repository audit. They are not findings claimed by the catalogs.

## Data gates used in this document

| Gate | Meaning | Concrete Stack Stats examples |
| --- | --- | --- |
| **P: Public now** | Already in the resolved public profile, respecting the existing synced/manual fallback. | Aggregate additions/removals; language percentages; six headline totals. No daily arrays. |
| **A: Aggregate/API addition** | Measurements exist in private cloud daily aggregates, but need a deliberately published, bounded aggregate response. Existing publication of totals does not authorize publication of dates. | Daily minutes, daily edits, language activity over dates, weekday summaries. |
| **U: Upload-contract addition** | Measurements exist locally, but the current sync projection discards the necessary dimensions. Requires an explicit new local reducer, upload contract, and publication consent. | Hour bins, weekday × hour, project × language edges, session distributions, project-switch sequences. |
| **N: New evidence** | Current activity telemetry does not establish the proposed meaning. Requires additional consensual evidence and validation, possibly new collection. | Framework/task/domain evidence, validated role labels, meaningful skill dimensions. |

The local extension has timestamped intervals, session snapshots, and joint project/file/language contributions; this does **not** make them current cloud or public data. UTC hourly aggregation exists locally, but there is no public hourly API. Choosing UTC, recorded timezone, or local calendar semantics must be part of any future contract. Do not reinterpret historical events using a viewer's timezone.

Public aggregate file counts are file-days, not unique lifetime files. Project identities may differ between installations. Language share uses tracked active time, with edit-count fallback when active time is zero. Edit additions/removals are not Git contributions, repository size, correctness, or productivity. Preserve source-aware wording: automatically tracked activity is not cryptographically verified truth; manually entered profiles remain manual.

## Every requested chart: verdict and truthful mapping

**A — strong fit now; B — strong fit later; C — experimental/profile showcase; D — not a good fit.** “Complexity” includes responsive layout, explanation, accessibility, and honest scales, not just drawing a path. C can still be worth doing: it means its value is visual identity or exploration, with more interpretation cost.

| Requested chart | Verdict | Dataset and meaning | Truthfulness requirements | Impact / complexity / data gate |
| --- | --- | --- | --- | --- |
| **Line graph** | **B** | One metric per observed date, such as tracked coding minutes or edits. Shows change through time. | Date spacing must be real; unknown coverage is a gap, not automatically zero. Preserve units and avoid joining unrelated metrics. | Clear, familiar; low–medium. **A** for a published daily series. Current totals cannot produce a line. |
| **Polar area chart** | **A** | Equal-angle language sectors, with sector **area** proportional to published share. A language bloom is a distinctive profile signature. | Use square-root radius; with a hole use `r² − innerRadius² ∝ value`. Fixed category order and explicit percentage labels. No “skills” interpretation. | High visual impact; medium. **P**, no new collection/API. |
| **Radial bar chart** | **A** | Concentric rings whose sweep angles show individual language percentages on a common 0–100% scale. | Angle, not arc length or filled area, encodes the value. Outer rings are not worth more. Explain the encoding and print values. | Strong identity and screenshot value; medium. **P**. |
| **Radial histogram** | **B** | Circular time bins, ideally 24 hourly bins of activity; initially a seven-day circular bar summary is also possible. | A histogram needs real bins, fixed angular width, declared UTC/local-time basis, and coverage. Do not turn unordered languages into a fake clock. | Strong “coding rhythm” signature; medium. Hourly: **U**. Weekday aggregate: **A**. |
| **Radial line graph** | **B** | A periodic activity curve across hours or weekdays. | Close the curve only for a genuinely cyclic domain. Label bins and retain gaps; do not smooth across missing coverage. | Visually useful compact rhythm; medium. Hourly **U**, weekday **A**. |
| **Waterfall plot** | **A** | Start at zero edit balance, add tracked additions, subtract tracked removals, finish at signed net edit balance. | Label it “edit balance,” not current codebase size. These totals do not establish intermediate chronology. Handle negative net and zero honestly. | Readable and distinctive for code changes; medium. **P**. |
| **Radar diagram** | **C** | Same-unit language shares on named axes could form an activity fingerprint; future comparable, explained activity dimensions could be another dataset. | Current mixed totals (minutes, files, edits, projects) cannot be thrown onto one radar. No invented skill ratings. Axis ordering changes the polygon; area is not a total or score. | Dramatic but easy to overinterpret; medium. Language variant **P**; credible role/skill variant **N**. Not selected for initial implementation. |
| **3D stream graph** | **C** | Time × language category × activity as separated ribbons, or an extruded stacked streamgraph. | Ribbon thickness must encode an actual time series. Depth must be declared categorical or decorative. Do not substitute scientific flow vectors for activity data. Provide a readable 2D view. | Absurd in a potentially excellent way; high. Language timelines **A**; project-language ribbons **U**. |
| **Transit map** | **C** | Projects and languages as stations/lines; a connection means measured activity in that project-language pair. | Layout distance has no geographic, skill, or semantic meaning. Current separate marginals do not establish joint edges. Project labels require explicit publication. | Could become a recognizable Stack Stats map; high. **U**. |
| **Topography map** | **B** | Contours over a weekday × hour activity matrix; height/color represents measured intensity, with optional disclosed interpolation. | Axes must remain visible. This is an activity surface, not physical geography. Interpolation creates a visual estimate between bins, not new observations. Zero and unknown coverage remain distinct. | Excellent signature-chart candidate; high. Hour matrix **U**. A week × weekday calendar terrain is possible with **A**, but has different adjacency semantics and must be named accordingly. |
| **Cluster analysis** | **C** | A future cohort feature matrix could group similar activity patterns; an embedding could show local similarity. | Clustering is an analysis step, not a chart or role detector. Python does not establish “AI engineer”; clusters are not skill rankings. Publish evidence and limitations, not precise invented role percentages. | Potentially compelling but research-heavy; very high. Activity-pattern clustering needs consented cohort **A/U**; professional archetypes need **N**. |
| **Candlestick chart** | **D** | Ordinary OHLC assumes a measured quantity observed repeatedly within each period. Current daily totals do not have open/high/low/close values. | “First session, longest session, shortest session, last session” mixes unrelated semantics; do not call that OHLC. A session-duration box/range plot would be truthful with appropriate quantiles. | Familiar market aesthetic but weak meaning here. True intra-period signal would require a defined **U/N** dataset; reject for release. |
| **Radial area chart** | **B** | Filled periodic curve of hourly/weekday activity. Distinct from equal-angle independent polar-area sectors. | Filled radius visually amplifies values. State whether radius or area encodes quantity; prefer area-correct encoding or a clear radial scale. Closure requires cyclic time. | High, especially paired with temporal color; medium. Weekday **A**, hourly **U**. |
| **Spline graph** | **B** | A smoother presentation of a daily metric, sharing the same adapter as line charts. | Sampling remains daily. Use interpolation that does not create negative values/overshoot, mark observations, and describe smoothing. No connecting missing periods. | Polished rather than radical; medium. **A**. |
| **Sparkline** | **B** | Compact daily metric history next to a total and date range. | A tiny line still needs the metric, units, period, missing-data policy, and accessible values. A scalar total is not a history. | Excellent resume readability; low–medium. **A**. |
| **Multiple-series 3D bar chart** | **C** | Day × language bars, height = one consistent activity measure. | Avoid hiding back bars; fixed camera screenshot must remain interpretable. Equal scales and 2D alternative. Never put mixed units on one height axis. | Visually loud but occlusion-prone; high. **A** for daily language marginals. |
| **Layered area chart** | **B** | Daily language active time stacked by language, or a clearly labeled 100% share timeline. | Layers need nonnegative additive quantities and aligned dates. Absolute time and percentages are separate modes. State grouping into “Other”; total missing days cannot be filled as zero without coverage evidence. | Strong evolution story; medium. **A**. |
| **3D scatter plot** | **C** | Each day as an observation with three explicitly labeled metrics (e.g. active minutes, edit count, changed file-days), or future consented cohort vectors. | A single aggregate profile is only one point. Do not invent positions or derive “skill space” from arbitrary axes. Offer projection/small multiples and exact values. | Impressive in motion, weaker in a static resume; high. Day observations **A**, archetypes **N**. |
| **Dot chart** | **A** | Horizontal dot positions show language percentages on a shared scale, or paired additions/removals in the same line-count unit. | A dot's position encodes value; decorative glow/size is constant. Include labels and a zero baseline for intuitive comparison. | Compact, crisp, very readable; low. **P**. |

The distinction between a streamgraph and a scientific streamtube is substantive: [streamgraphs](https://www.data-to-viz.com/graph/streamgraph.html) stack changing series, whereas [Plotly streamtubes](https://plotly.com/javascript/reference/streamtube/) require spatial positions and vector components. Stack Stats has no physical vector field. Similarly, [chord diagrams](https://www.data-to-viz.com/graph/chord.html) need measured weighted edges; marginal language/project totals are insufficient.

## Chart ↔ dataset compatibility matrix

This is the complete **planned semantic** matrix, including future-only datasets; it is not a claim that every row has an implemented adapter. Renderers should be registered against explicit dataset identifiers and shapes, not enabled by a shared “number array” type.

| Dataset / shape | Units and constraints | Compatible presentations | Gate / incompatible examples |
| --- | --- | --- | --- |
| `language_share` / categorical share | Named published percentages; finite nonnegative values; disclose manual versus tracked source and any incomplete total. | Bars, dots, radial rings, polar-area bloom, donut; later treemap or waffle. | **P**. Not line, sparkline, time histogram, or topography. A percent is not proficiency. |
| `line_changes` / signed composition | Added/removed line counts in one period/source; derived net may be negative. | Bars, dots, diverging bars, waterfall; a donut is possible only for gross added-vs-removed composition, never signed net. | **P**. Not mixed-unit radar or time series. |
| `headline_total` / scalar with unit | One of the six existing totals; units remain distinct. | Numeric headline; later a comparison bullet only if a real user-defined target exists. | **P**. Not an invented timeline, percentile, completeness gauge, or skill meter. |
| `daily_activity` / dated single series | Date, value, unit, coverage, period; per-installation local dates require a documented merge policy. | Line, monotone spline, sparkline, area, calendar heatmap, horizon strip; daily distribution with a declared sample set. | **A**. A daily total cannot support hourly patterns or session quartiles. |
| `daily_language_activity` / dated series collection | Date × language × active time or edit count; use one measure consistently. | Layered area, streamgraph, bump/rank chart, small multiples; experimental 3D ribbons/bars. | **A**. Never combine time-based shares with edit-based shares silently. |
| `weekday_activity` / cyclic seven-bin summary | Sum or average per observed weekday, with denominators and coverage. | Circular/radial bars, radial line/area, ordinary bars. | **A**. “Average Monday” requires observed Monday count, not all calendar Mondays. |
| `hour_activity` / cyclic 24-bin summary | Activity by UTC or recorded timezone; explicit bins and coverage. | Radial histogram, radial line/area, clock heatmap. | **U**. No claim of productivity or working availability. |
| `weekday_hour_activity` / numeric grid | Two declared temporal axes, one intensity measure, coverage per bin. | Heatmap, contour/topography, ridgeline over hours, optional 3D surface. | **U**. Surface interpolation is not measured sub-hour precision. |
| `project_language_activity` / weighted bipartite graph | Joint project-language measurement; sanitized/consented labels and stable identity policy. | Transit map, Sankey, chord, adjacency matrix, arc diagram, network; project → language hierarchy if explicitly nested. | **U**. Independent marginals cannot be multiplied into pretend edges. |
| `session_duration_distribution` / sample or quantiles | Sessions with consistent start/end and idle semantics; sample size, period, coverage. | Histogram, ECDF, box/range, violin, ridgeline. | **U**. Sum + session count gives a mean, not distribution/quantiles/OHLC. |
| `project_switch_sequence` / ordered transitions | Observed ordered contexts and timestamps; explicit gap handling. | Arc trail, transition matrix, alluvial paths, sequence/raster plot. | **U**. Cloud per-day project totals do not contain ordering. |
| `day_activity_vectors` / observations × metrics | Multiple dates with separately scaled measures and declared units. | 2D scatter, parallel coordinates, correlation matrix; experimental 3D scatter. | **A**. Correlation is not causal impact or talent. |
| `activity_archetype_evidence` / validated features and evidence | Consented context, stable feature definitions, sufficient coverage, evaluation set and unknown state. | Evidence cards, explained feature bars; research embedding/cluster map, carefully normalized radar. | **N**. No automatic professional role labels from language IDs alone. |

Compatibility has two stages: structural validity (shape, unit, sign, series count) and availability (public permission, observation coverage, nonempty data). Both must pass. A chart appearing in a future registry must never cause the profile renderer to fetch private telemetry. Selectable UI choices should say things like “Languages” and “Radial rings,” not expose these internal identifiers.

## First release selection: six now, two gated follow-ups

| Presentation | Why it made the cut | Release status |
| --- | --- | --- |
| Horizontal bars | Fast comparison, readable at half width, a useful anchor among more expressive styles. | Current public data. |
| Dot chart | Compact and premium-looking without needing another metric; preserves a shared scale. | Current public data. |
| Radial rings | Strong profile individuality; printed percentages make the decorative ring arrangement understandable. | Current public data. |
| Language bloom / polar area | The “what is that?” showcase choice. The unusual silhouette is generated by actual language shares using area-correct geometry. | Current public data. |
| Segmented donut | Familiar part-to-whole reference and existing product visual language; new appearance configuration can make it personal. | Current public data, with complete/explicitly disclosed share semantics. |
| Code-change waterfall | Gives additions/removals a distinct visual vocabulary instead of reusing language charts everywhere. | Current public data. |
| Daily line / sparkline family | Introduces genuinely temporal evidence, with a compact choice for resumes. | **Blocked on a new opt-in public daily aggregate API.** No fake preview values from a scalar. |
| Calendar heatmap | Recognizable long-term rhythm, easy screenshot scanning, good entry point to later contour/terrain experiments. | **Same public daily aggregate gate.** Coverage/unknown days must be designed first. |

This roadmap deliberately does not claim to ship temporal or 3D charts before their required public data exists. An exceptional later surface needs a larger **U** contract addition; a line/heatmap needs the smaller **A** publication/aggregation addition. Neither is implemented by silently broadening today's totals-sharing setting.

For the current share charts, incomplete manual percentages need an explicit policy. Do not silently renormalize 40% + 20% into 67% + 33%. Either show the supplied percentages on a fixed scale and annotate their total, or show an explicitly labeled unallocated remainder when a part-to-whole renderer requires it. The implementation preserves the existing manual rounding tolerance: an excess of at most 0.01 percentage points is adjusted to 100% with an explanatory note, without changing saved values. Larger over-100% totals show an unavailable-data explanation instead of a plausible-looking complete pie.

## Experimental lab

These are intentionally extravagant. Prototype them only against real opt-in test data with a readable static fallback.

1. **Floating language rivers:** 3D ribbons over time, one per language. Depth identifies the language; ribbon thickness encodes activity. Do not imply physical flow or add particle speed as an unexplained metric.
2. **Coding terrain island:** a lit weekday-hour surface with contour lines and a static top-down default. Lighting changes appearance, not values; the height/color legend must survive a screenshot. [Plotly's surface gallery](https://plotly.com/javascript/3d-surface-plots/) establishes the grid requirement.
3. **Orbital activity calendar:** each ring is a week and each angular segment is a day, with intensity as color. Orbital position is a date encoding; no fake planet mass, gravity, or “importance.”
4. **Project-language circuit board:** transit-map edges routed at right angles with measured thickness. Decorative routing lengths never imply effort or distance.
5. **Extruded language skyline:** one tower per language, height encoding share, fixed camera, front labels, and 2D comparison toggle. Footprint/volume must not accidentally become a second quantitative encoding.
6. **Double-helix edit trail:** separate additions/removals along real dates; radius or mark length encodes counts. Never generate a chromosome from aggregate totals and imply historical detail.
7. **Developer constellation:** an opt-in activity-pattern embedding with a selected user's point. This is a research view of similarity under a declared model, not a hiring rank or an inferred professional identity.
8. **Animated contour pulse:** scrub real days or weeks through a surface, with reduced-motion/static modes. Interpolated transitions are animation, not intermediate measurements.

## Developer archetypes: research direction, not a classifier

Activity records describe what was observed, not all professional work. The [SPACE research paper](https://www.microsoft.com/en-us/research/publication/the-space-of-developer-productivity-theres-more-to-it-than-you-think/) treats developer productivity as multidimensional; activity counters alone should therefore not become a talent score. This is particularly important on resumes and job applications.

### Evidence required

| Desired interpretation | Evidence that could help | What existing language/time totals cannot establish |
| --- | --- | --- |
| Frontend/mobile | Consented project purpose and framework/platform evidence; user-confirmed work categories; representative coverage. | JavaScript/TypeScript or Swift alone does not establish frontend/mobile responsibility or competence. |
| Backend/platform/DevOps | Declared service/infrastructure work and validated tool/dependency categories, with task context. | Shell/YAML activity is not proof of DevOps expertise. |
| AI/data engineering | User-approved project/task categories and locally derived evidence of relevant tooling/workflows, validated against a labeled research set. | Python, notebooks, or generic AI attribution fields do not prove AI engineering. |
| Systems engineering | Project context and low-level domain evidence, then user confirmation and external validation. | C/C++/Rust activity alone does not establish systems expertise. |
| Full-stack / mixed practice | Sustained evidence across multiple confirmed domains; permit multiple labels. | A broad language list is not automatically full-stack work. |

Do not implement source-code uploads or semantic analysis in this release. A future research phase could investigate **local, opt-in derivation** of coarse dependency/framework/task categories. It must first define what counts as evidence, what stays on-device, how users can inspect/correct it, and how withdrawal/deletion works. Tool/package names and project relationships can themselves disclose confidential work, even without code.

### Analysis and representation

Begin with a transparent feature table and user-confirmed descriptors; compare clustering against simple explained baselines. Use normalized activity shares/rates with declared coverage windows, not absolute volume as a proxy for skill. Keep role labels separate from unsupervised cluster identifiers. Validate stability across resampling, time periods, platforms, missing coverage, and model versions; support mixed and unknown assignments.

An embedding may support exploratory similarity, but it does not provide calibrated job-role probabilities. The authors of [How to Use t-SNE Effectively](https://distill.pub/2016/misread-tsne/) show that apparent cluster sizes and distances can mislead. [UMAP's clustering documentation](https://umap-learn.readthedocs.io/en/latest/clustering.html) likewise explains caveats around density and apparent clustering. Prefer “Activity pattern resembles these examples, using these features” plus evidence coverage to “87.3% AI engineer.” A 3D embedding is a presentation option, not better evidence.

Require separate consent for cohort analysis and for displaying a public comparison. Avoid exposing identifiable neighbors, rare-project signatures, employer/client names, precise working hours, or tiny cohort groups. Do not infer protected traits, employability, productivity, or seniority. Provide an opt-out and correction path; unknown/inadequate evidence is a valid result.

### Practical acceptance criteria

The first render should contain the actual chart and readable values, with no random geometry, fake placeholders, layout jump, or animation needed to understand it. Half-width modules must remain legible on a phone. More expensive future renderers should load only when selected, have a static screenshot-friendly default, cap data/geometry complexity, pause offscreen, respect reduced motion, and retain a no-WebGL fallback.

Color is part of the data contract. Categorical palettes identify groups; sequential palettes encode increasing magnitude; diverging palettes encode signed change around a meaningful midpoint. Do not use a categorical rainbow as a numerical intensity scale. Offer restrained and expressive presets plus a high-distinguishability option, but do not promise universal colorblind safety from a palette name.

Renderer capability declarations should show only useful controls: category colors for language segments, positive/negative/total colors for waterfall, a primary line/fill for a future sparkline, and low/mid/high gradient stops for a future surface. Keep body text and axis labels readable independent of decorative palette choice. [WCAG non-text contrast](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html) and [use of color](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html) support checking essential graphical contrast and providing labels/patterns rather than communicating meaning through color alone. A minimum contrast check against the background is useful but does not prove that adjacent series are distinguishable; retain exact labeled values.
