Audited 2026-09-25 against the web checkout and, read-only, the local engine at `/Users/fstopyra/Desktop/projects/stack-stats`. This is a code/contract audit, not inspection of anybody's activity records. Availability in the local engine does **not** mean that data is uploaded or public.

## What the profile can use today

The public route loads public manual values, then replaces their displayed statistics only when the separate publication RPC returns uploaded records. The owner editor receives that same public result; ownership is not permission to silently render private history on a public profile. An unavailable RPC or disabled publication falls back to the saved manual source. When synced totals are public but synced languages are private, language data remains empty; manual languages must not be substituted. See [profile route](../src/app/u/[username]/page.tsx), [source adapter](../src/lib/synced-profile.ts), [profile metrics](../src/lib/profile-metrics.ts), and [publication controls](../src/components/dashboard/sync-privacy.tsx).

| Input | Available shape / granularity | Meaning and limitations | Publication |
| --- | --- | --- | --- |
| `lines_added`, `lines_removed` | Nonnegative aggregate integers | Manual values, or gross recorded editor line-boundary changes. Synced values include undo/redo; these are not Git diff totals, remaining codebase size, authored code, quality, or productivity. | Public manual fields; synced replacements require `publishProfile`. |
| `edit_events` | One aggregate integer | Recorded editing operations, not keystrokes, commits, tasks, or meaningful accomplishments. | Same totals permission. |
| `coding_minutes` | One aggregate integer; synced adapter floors `activeMs / 60000` | Estimated evidenced coding time. Overlapping collectors may overlap in the sum; this is not unique human time or hours at work. | Same totals permission. |
| `files_changed` | One aggregate integer | Manual “Files changed”; synced “File-days”: distinct recorded files **per installation per day**, summed over days. Not unique lifetime files. | Same totals permission. |
| `projects_count` | One aggregate integer | Manual “Projects”; synced count of installation-scoped pseudonymous project identities. A repository on two devices can count twice. | Same totals permission; project identifiers themselves stay private. |
| `languages` | `{id, name, percentage}` rows | Synced shares use accumulated language active time; if total time is zero, accumulated edit counts; if both are zero, zero shares. Raw VS Code IDs survive; names are display-normalized. Manual percentages are self-reported. | Manual public rows, or separately opted-in synced language breakdown. |
| `updated_at` | One timestamp | Last manual profile update or latest cloud receipt for published records. Not last edit time, historical observation time, or a time-series point. | Public. |
| Identity, links, appearance, layout | Public presentation fields | Useful labels and presentation settings, not activity observations. | Public profile. |

The public RPC additionally returns `recordCount`, `activeMs`, `fileDays`, `projectCount`, and per-language `activeMs`, `editCount`, `linesAdded`, `linesRemoved`. The current `withSyncedProfile` adapter converts these into the fields above and discards per-language counts and exact milliseconds. An adapter could expose already-approved raw language counters later without new collection or broader publication, but manual profiles have no equivalent absolute language counters. Do not manufacture language minutes by multiplying a manual percentage by an unrelated total.

Safe immediate dataset shapes are **language composition** (percentage, explicitly describing its source) and **line-change arithmetic** (added, removed, difference). A waterfall can show `0 → added → added − removed` as an arithmetic bridge; label it as recorded line changes, never repository growth. Bars, dots, radial bars, area-scaled polar sectors, and a donut can all encode the same language shares. Separate mixed-unit headline counts must not be treated as a comparable radar vector or percentages of one total.

## Cloud data that exists but is private

The authoritative schema and functions are in [profile sync migration](../supabase/migrations/20260910000000_profile_sync.sql), with the strict portable payload in [sync contract](../src/lib/sync-contract.ts) and browser endpoint validation in [sync API](../src/lib/sync-api.ts).

| Layer | Current shape | Granularity / semantics | Visualization implications |
| --- | --- | --- | --- |
| `sync_days` | Key `(user_id, installation_id, date)`, revision, JSONB payload, server `updated_at` | One canonical replacement snapshot per installation and recorded local calendar day; retries do not add copies. | Daily history exists server-side. No public date-series API exists. |
| Daily counters | `activeMs`, `editCount`, `linesAdded`, `linesRemoved`, `sessionCount`, `fileCount` | Nonnegative integers. Session count is contributing sessions for that day; file count is distinct local project/file identities on that day. | Daily coding/edit/line series, weekday aggregates, calendar maps and daily distributions need SQL aggregation, not new collector signals. |
| Daily language rows | `{id, activeMs, editCount, linesAdded, linesRemoved}` | Allowed standard language IDs; custom languages become `other`; per-day totals reconcile to daily totals. | Language-over-days series and honest stacked temporal layers are recoverable privately. |
| Daily project rows | `{id, activeMs, editCount, linesAdded, linesRemoved}` | Salted HMAC pseudonyms scoped to account + installation; no names; totals reconcile separately to daily totals. | Project-over-days series are recoverable privately. Names require deliberate owner labels, never reverse engineering. |
| Private summary | `schemaVersion`, `from`, `to`, four activity counters, `sessionDays`, `fileDays`, `projectCount`, `activeDays`, `recordCount`, `updatedAt`, `activeDates`, language totals, project totals including installation IDs | Existing RPC/HTTP endpoint aggregates 7/30/90 days or lifetime for the authenticated owner. It returns totals and active-date membership, **not daily count rows**. | Existing `activeDates` can support an owner's private binary activity calendar/streak calculation. Intensity needs new grouped daily output. |
| Privacy | `publish_profile`, `publish_languages` | Both default false; uploading, publishing totals, publishing languages are distinct approvals. | Adding a visible layout module changes presentation only; it must not broaden publication. |

All cloud sync tables have RLS enabled and no direct browser/extension-role table privileges. `sync_aggregate` is not executable by those roles. The public wrapper builds an explicit field allowlist; it omits individual dates, installation/project identifiers, sessions, time windows, and active-day arrays. Its actual allowlist **does include `fileDays`**, despite an imprecise adjacent legacy comment. The private summary derives the owner from `auth.uid()`; upload credentials cannot read it or change publication. [Documented contract and consent](SYNC.md).

Language and project arrays are **marginals**, not a joint table. A day containing TypeScript + Python and projects A + B does not tell us which language belongs to which project. A transit/network/Sankey renderer must never invent those edges.

## Constraints for temporal and cluster work

1. **Dates are recorded local calendar dates.** Uploaded history does not carry a timezone identifier. UTC endpoint defaults govern range bounds; they do not turn the payload's date into a UTC activity day. Multiple installations and travel complicate interpretation. Publish labels that describe the actual calendar semantics.
2. **Missing is not zero.** Sync can begin with a 90-day upload window, pause, fail, exclude projects, or lack old session/raw history. A missing row means “no uploaded observation”; do not connect gaps, interpolate activity, or claim inactivity without coverage evidence. A recorded zero row is different.
3. **Time and counts can overlap.** Cross-device/editor work is not globally deduplicated. A day can exceed 24 accumulated hours. Never silently clamp it into a human-hours claim.
4. **Privacy is independent of layout.** History, time-of-day habits, pseudonymous project relationships and distributions disclose more than lifetime totals. Add aggregate/publication APIs explicitly; do not call the private summary from a public renderer or reuse owner-only payloads for screenshots/public caching.
5. **No fake skills.** Language usage is evidence of observed language activity, not “Python expertise 87%”, AI engineering, or employment seniority. TypeScript/Python can serve many roles. Build/test/Git counts are also not competence scores.
6. **Clusters need a population and uncertainty.** A defensible future feature uses opt-in activity feature vectors, coverage gates, cohort normalization, unsupervised clusters with careful descriptive labels, optional user-confirmed roles, and an explicit unknown/mixed state. Validate whether labels correspond to independently supplied evidence before making role claims. Embedding distances/axis directions and cluster IDs are model artifacts, not percentages of skill. Keep artifacts versioned; explain instability as cohorts/models change; do not use protected traits or infer sensitive categories.

## Persistence upgrade boundary

The existing [layout migration](../supabase/migrations/20260924000000_profile_layout.sql) permits **exactly version 1 and exactly four known singleton sections**. Its CHECK and `update_profile_layout` both invoke the validator. A visualization cannot safely be persisted as an extra field/row under version 1.

The additive [visualization migration](../supabase/migrations/20260925000000_profile_visualizations.sql) preserves that validator as a version-1 helper and replaces the original function **in place** with version dispatch. Renaming the original function alone is insufficient: the CHECK retains its original function OID and would continue enforcing only v1. Both v1 and the bounded v2 format remain valid; the migration does not rewrite existing rows, alter RLS, grant new profile access, or change publication APIs. Layout-only edits continue preserving profile freshness. Apply the migration before deploying UI that can save v2; older clients must decline editing unknown layout versions. Unknown future renderers should be explained to the owner and omitted publicly, while keeping the stored configuration intact and disabling editor saves that would discard it.
